# ADR-012: Stem Category — Fixed Enum, Not Free-Text

## Status: Accepted

## Date: 2026-07-22

## Context

`stems` table originally had a `name` column, intended to store a
user-provided stem label (e.g. "Lead Vocals", "808 Bass"). In practice
this conflated two different things: an identifier for the stem's
_type_ (what category of sound it is) and a display label — but a
stem's display name is always derivable as `${song.title} — ${category}`,
so storing a separate free-text `name` created a second source of truth
for something that should be computed, not persisted.

This surfaced while designing `app/actions/add-stem.ts` for v0.5 Song
Management: allowing arbitrary user input for `name` would let the same
type of stem be recorded inconsistently across uploads (`"Vocals"` vs
`"vocal"` vs `"Lead Vox"`), making future filtering/grouping by stem type
unreliable without a normalization pass.

## Decision

Replace `stems.name` with `stems.category`, typed as a Postgres enum
(`stem_category`) with a fixed set of values:

```sql
create type stem_category as enum (
  'vocals', 'drums', 'bass', 'melody', 'guitar', 'synth', 'fx', 'other'
);

alter table stems drop column name;
alter table stems add column category stem_category not null;
```

`other` is the catch-all for anything outside the fixed set — users do
not get a free-text category field. Display name is computed at render
time (`${song.title} — ${category}`), never stored.

## Alternatives Considered

**Free-text `category` (`text` column, no constraint)**

- Maximum flexibility — user can label a stem however they want
- Rejected: no consistency guarantee, breaks any future filter/group-by
  feature, and re-introduces the same problem `name` had — just renamed

**`text` + `CHECK (category in (...))` instead of native Postgres enum**

- Easier to extend — adding a value is `ALTER TABLE ... DROP CONSTRAINT` +
  `ADD CONSTRAINT`, no `ALTER TYPE` ceremony
- Rejected for now: native enum gives free type generation in
  `database.types.ts` (`Database["public"]["Enums"]["stem_category"]`),
  which is more valuable at this stage than the marginal ease of adding a
  category later — categories are not expected to change often

**User-defined categories (separate `stem_categories` table, FK from `stems`)**

- Fully extensible, no migration needed to add a category
- Rejected: over-engineered for 8 fixed categories at portfolio scale;
  adds a join for no present benefit

## Consequences

- `stems.name` no longer exists — any code referencing it (forms, display
  logic) must be updated to use `category` + derived display name
- `types/database.types.ts` regenerated — `stem_category` enum now
  available as `Database["public"]["Enums"]["stem_category"]`
- Adding a new category requires a migration (`ALTER TYPE ... ADD VALUE`)
  — acceptable at current scale, revisit if categories need to change
  frequently
- `app/actions/add-stem.ts` takes `category: StemCategory` instead of
  `name: string`
