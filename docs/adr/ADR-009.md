# ADR-009: Discord OAuth via Popup Window, Not Full-Page Redirect

## Status: Accepted

## Date: 2026-06-19

## Context

Original plan (ADR-005) used `signInWithOAuth()` with a full-page redirect.
Clicking the Discord button caused a brief flash of Zod validation errors
across `RegisterForm` before navigation — likely tied to full-page
navigation interacting with `mode: "onBlur"`, root cause not fully
isolated. Decision: open Discord OAuth in a popup instead, so
`RegisterForm`/`LoginForm` never unmount.

## Decision

**`hooks/auth/use-social-login.ts`** (provider-agnostic) —
`signInWithOAuth()` with `skipBrowserRedirect: true`, opens `data.url` via
`window.open()`, resolves `{ error: Error | null }` once the popup closes
(ADR-008 contract). **`hooks/auth/use-discord-login.ts`** (thin
per-provider wrapper) owns the parent session sync — see below. The split
separates OAuth/popup mechanics from Discord-specific side effects (toast,
session refresh, modal close) — useful now, with one provider, not only as
prep for future ones.

**`app/auth/callback/route.ts`** no longer redirects — runs only inside
the popup, returns self-closing HTML instead of
`NextResponse.redirect()`. Original Supabase-docs boilerplate (`next`
param, `forwardedHost`, `/auth/code-error`) removed entirely.

**Popup→parent: `localStorage`, not `postMessage`.** `window.opener` was
`null` inside the popup in this environment (verified via console log,
no COOP header set anywhere) — `postMessage` never fired, so
`localStorage` is used as a working substitute:

```ts
// popup (auth/callback/route.ts response body)
localStorage.setItem(
  "discord-oauth-result",
  JSON.stringify({ success, ts: Date.now() }),
);
window.close();
```

```ts
// parent (use-social-login.ts)
const checkClosed = setInterval(() => {
  if (popup?.closed) {
    clearInterval(checkClosed);
    const raw = localStorage.getItem("discord-oauth-result");
    localStorage.removeItem("discord-oauth-result");
    // raw + success → resolve({ error: null })
    // raw + !success → resolve({ error: new Error("Discord sign in failed") })
    // no raw → resolve({ error: new Error("Popup closed before completing sign in") })
  }
}, 500);
```

`localStorage` is cleared both before opening the popup (stale result) and
after reading (avoid resolving a future attempt). Note: `window.open()`
returning `null` (popup blocker) is not yet handled — known gap.

**Parent session sync.** Cookies are set server-side inside the popup's
request, so the parent's in-memory Supabase client doesn't auto-detect the
new session. `use-discord-login.ts` calls `refreshSession()` before
`router.refresh()` to force `onAuthStateChange` in the parent — without
this, `onAuthStateChange`-driven UI (navbar) only updates on manual reload.

`code` missing from the query string, or `exchangeCodeForSession()`
returning an error, both resolve to `popupResponse(false)` — the popup
always closes with a definitive success/failure signal, never hangs open.

## Alternatives Considered

**Keep full-page redirect, fix the validation-flash directly**
(`onMouseDown` + `preventDefault()`)

- Rejected: popup OAuth was the preferred UX (SoundCloud reference)
  independent of the validation-flash bug — the bug triggered the
  investigation, not the sole justification

**`postMessage`** (original implementation)

- Rejected: unusable once `window.opener` was confirmed `null`

**Poll `getUser()` from the parent, no message channel**

- Rejected: can't distinguish "in progress" from "closed without
  completing" — `popup.closed` check is still required either way, so
  `localStorage` adds near-zero extra cost

## Consequences

- `auth/callback/route.ts` is popup-only, not reusable for a future
  full-page flow without branching
- `use-social-login.ts` owns popup lifecycle — meaningfully more code
  than a bare `signInWithOAuth()` call, justified by UX parity
- `refreshSession()` + `router.refresh()` required after popup close, or
  `onAuthStateChange` consumers only update on manual reload
- Future OAuth providers reuse this pattern or get their own — not
  decided, no second provider exists yet
