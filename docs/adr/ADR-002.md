# ADR-002: Upload Architecture — Route Handler, R2 Transaction Safety, and Delete Flow

## Status: Accepted

## Date: 2026-03-19

## Context

The upload feature requires handling large audio files (WAV/MP3 stems, up to 200MB) alongside metadata storage in Supabase. Two architectural questions arose during planning:

**1. Route Handler vs Server Action for upload endpoint**

Next.js Server Actions handle `FormData` natively and would keep upload logic consistent with the rest of the codebase (`app/actions/`). However, audio files can reach 200MB — well above the default body size limits that apply to Server Actions. Route Handlers give explicit control over body parsing, size limits, and streaming behaviour.

**2. Transaction safety between R2 and Supabase**

R2 and Supabase are two independent services with no shared transaction boundary.
A file can be written to R2 successfully while the subsequent Supabase insert fails — leaving an orphaned file in storage with no DB record. The reverse is also possible in delete flows: the DB record is removed but R2 files remain.

## Decision

**1. Use a Route Handler for upload — `app/api/upload/route.ts`**

Server Actions are used everywhere else in the codebase. Upload is the deliberate exception: file size requirements make Route Handler the safer and more explicit choice.

- Body parser disabled on the upload route via `next.config.ts`
- Size limit set explicitly to accommodate large WAV files
- Auth verified via `supabase.auth.getUser()` inside the handler before any R2 write
  This exception is intentional. All other data mutations remain in `app/actions/`.

**2. Manual rollback on upload failure**

On upload, files are written to R2 first, then the Supabase record is inserted. If the DB insert fails, all R2 files written in that request are deleted before returning an error to the client.

Upload order:

1. Write audio to R2 `songs` bucket
2. Write cover to R2 `covers` bucket
3. Write stems to R2 `stems` bucket
4. Insert record in Supabase `songs` table
5. Insert records in Supabase `stems` table
6. On any failure at steps 4–5: delete all files written in steps 1–3

**3. Cascading delete flow**

On song delete, Supabase record is removed last — after all R2 files are confirmed deleted. If any R2 delete fails, the path is logged for manual cleanup. The DB record
is not removed until all storage operations succeed.

Delete order:

1. Fetch all stem paths from `stems` table for the song
2. Delete audio from R2 `songs` bucket
3. Delete cover from R2 `covers` bucket
4. Delete all stem files from R2 `stems` bucket
5. Delete `stems` records from Supabase
6. Delete `songs` record from Supabase
7. On any R2 failure at steps 2–4: log orphaned paths, abort DB delete

## Alternatives Considered

**Server Action for upload**

- Consistent with rest of codebase
- Rejected: default body size limits are insufficient for large audio files;
  configuring limits on Server Actions is less explicit than Route Handler config

**Delete R2 files after DB delete**

- Simpler order of operations
- Rejected: the DB record is the only source of truth for R2 file paths. If the DB record is deleted first and an R2 delete then fails, there is no longer any record of which paths need cleanup — the orphaned files become permanently unidentifiable. Deleting R2 files first keeps the DB record available as a recovery reference for as long as any storage operation can fail.

**Supabase Storage triggers for cleanup**

- Could automate R2 cleanup via database triggers
- Rejected: R2 is not Supabase Storage — no native trigger integration;
  would require an external webhook adding unnecessary complexity

## Consequences

- Upload route is the only Route Handler in the codebase — document clearly in code with a comment referencing this ADR
- All song/stem server actions must verify caller owns the resource via
  `supabase.auth.getUser()` before executing — RLS covers DB layer,
  ownership check covers application layer
- Orphaned file logging requires a monitoring/alerting strategy before production
- `deleteFromR2` in `lib/r2/upload.ts` must be callable independently
  (used by both upload rollback and delete flow)

## Update — 2026-07-10

Resolved as a decision: scheduled reconciliation via Vercel Cron
(`app/api/cron/cleanup/route.ts`), diffing R2 objects against DB rows —
chosen over a manual on-demand script for zero ongoing cost and a stronger
portfolio artifact. Not yet implemented, tracked in `docs/TODO.md`.

## Update — [2026-07-22]

`updateSongCover` follows the same non-atomic-transaction principle as
upload/delete, applied to a replace operation: new file uploaded to R2
first, then DB `image_path` updated, then old file deleted from R2 last.
If the DB update fails, the newly uploaded file is deleted (rollback) so
a failed replace doesn't leave two orphaned files. If the old file's
final delete fails, it's logged and left for the orphaned reconciliation
cron (see Update 2026-07-10) rather than blocking the otherwise-successful
update — the user already has a working cover at this point, aborting the
whole operation over a stale file's cleanup would be a worse trade-off
than a temporary orphan.

## Update — 2026-07-22 (Stems in Upload Flow)

Stems now upload in the same request as the song, not as a separate
post-upload step. `uploadStem` (implemented since v0.3, unused until now)
activates: `app/api/upload/route.ts` accepts an optional array of stem
files + categories in the same `FormData`, uploaded to R2 `stems` bucket
as steps 3a/3b below, folded into the existing rollback.

**Revised upload order:**

1. Write audio to R2 `songs` bucket
2. Write cover to R2 `covers` bucket
3. Write each stem to R2 `stems` bucket (if any provided)
4. Insert record in Supabase `songs` table
5. Insert records in Supabase `stems` table (if any)
6. On any failure at steps 4–5: delete all files written in steps 1–3

This confirms Option B over Option A (calling `app/actions/add-stem.ts`
per file after song creation): Option A would let a song exist without
its stems on partial failure, breaking the all-or-nothing guarantee this
ADR already established for audio+cover. `add-stem.ts`/`delete-stem.ts`
(server actions, v0.5) remain the correct path for adding/removing stems
on an _existing_ song after initial upload — they are not used during
the upload flow itself.

**Consequence:** `uploadSchema` (`lib/validations/upload-schema.ts`)
gains an optional `stems` field; stem files are validated the same way
as audio/cover (MIME type + size in the route handler, not Zod — no
`File` in Node.js, consistent with the original decision above).

**Rollback extends to the `songs` record itself.** If the stems insert
(step 5) fails _after_ the `songs` insert (step 4) already succeeded, the
`songs` row is deleted in addition to the standard R2 rollback (steps
1–3) — otherwise a song would persist without its stems, silently
breaking the all-or-nothing guarantee. This is a case the original
decision (`## Consequences`, "on any failure at steps 4–5: delete all
files written in steps 1–3") didn't fully spell out: it covered the R2
side but not that a step-4 success followed by a step-5 failure also
requires undoing step 4 itself, not just steps 1–3.

## Update 2026-08-22 — cztery Route Handlery, nie jeden

`## Consequences` mówi "Upload route is the only Route Handler in the codebase — document clearly in code with a comment referencing this ADR". Oba człony są dziś nieaktualne.

Route Handlery są cztery: `app/api/upload/route.ts` i `app/api/cron/cleanup/route.ts` (ten drugi doszedł w Update 2026-07-10) oraz dwa auth-owe — `app/auth/callback/route.ts` i `app/auth/confirm/route.ts`. Te dwa istnieją z tego samego powodu co pozostałe: OAuth provider i klient pocztowy wchodzą pod adres HTTP z zewnątrz aplikacji, a server action nie ma adresu. Nie są wyjątkiem od tej decyzji, tylko jej kolejnym zastosowaniem.

Człon o komentarzu w kodzie nie obowiązuje — `docs/reference/CONVENTIONS.md` → "Komentarze" zabrania komentarzy wyjaśniających w tym repo. Uzasadnienie każdego handlera żyje w `docs/reference/CONVENTIONS.md` i w tym ADR, nigdy w pliku.

## Update 2026-08-22 — druga strona kolejności przy delete

`## Consequences` opisuje wyłącznie awarię po stronie R2. Kolejność przy usuwaniu jest odwrotna niż przy zapisie — najpierw pliki z R2, potem wiersz w bazie, bo to wiersz jest jedynym zapisem ścieżek do posprzątania — i ta kolejność ma własny tryb awarii, który nie był tu opisany: nieudany delete wiersza po udanym usunięciu plików zostawia utwór widoczny w aplikacji, którego audio, okładka i stemy zwracają 404.

`delete-song.ts` loguje teraz w tej gałęzi id utworu (odpowiednik istniejącego logu `orphanedPaths`) i zwraca komunikat mówiący wprost, co się stało. Cron sprząta wyłącznie w drugą stronę — obiekty R2 bez wiersza — więc automatycznego odzysku dla tego przypadku nadal nie ma; kandydaci (przebieg odwrotny w cronie albo soft delete) czekają jako D8.
