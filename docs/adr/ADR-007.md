# ADR-007: Profile Creation — User-Provided Nickname with Pre-Signup Uniqueness Check

## Status: Accepted

## Date: 2026-06-18 (extended 2026-06-19 for Discord OAuth)

## Context

`profiles` has no row created automatically by Supabase on signup — a
`handle_new_user()` trigger (`after insert on auth.users`) creates it,
written and run manually in Supabase Studio, not yet committed as a
migration.

Nickname source was initially `split_part(new.email, '@', 1)` inside the
trigger, with a collision-handling loop on the `unique` constraint (two
emails can share a prefix). This produced a nickname the user never chose,
with no chance to change it during signup — and a trigger failure on
`after insert` rolls back the entire `auth.users` insert, so any
collision surfaced as a generic Supabase error, not a readable message.

## Decision

`nickname` is a required, user-chosen form field, validated for uniqueness
**before** `signUp()` — not generated or deduplicated inside the trigger.

**Flow:** Zod validates format in `registerSchema` (`lib/validations/auth.ts`)
→ `hooks/use-register.ts` checks `profiles` for an existing row with the
same `nickname` before calling `signUp()`; on conflict, returns
`Error("Nickname already taken")` without creating an Auth user → trigger
inserts `nickname` from `raw_user_meta_data` as-is, no generation or
dedup logic.

**Format constraints** (relaxed 2026-06-19 to accommodate Discord
usernames, which may contain `.` and run up to 32 chars):

```
.min(3, "Nickname must be at least 3 characters")
.max(32, "Nickname must be at most 32 characters")
.regex(/^[a-zA-Z0-9_.-]+$/, "Only letters, numbers, underscores, dots and hyphens allowed")
```

**Case-insensitive uniqueness** — `nickname` is lowercased in
`use-register.ts` before both the check and `signUp()` (`.eq()` and the DB
`unique` constraint are case-sensitive by default; `Jan`/`jan` would
otherwise pass as distinct). Trade-off: original casing is not preserved.
Fix, if ever needed: separate `nickname_lower` column with the constraint
moved there — not implemented.

**Discord OAuth extension (2026-06-19)** — `signInWithOAuth()` bypasses
`use-register.ts` entirely, so there's no Zod validation, uniqueness
check, or lowercase step for OAuth accounts. `handle_new_user()` covers
both paths in one function via `coalesce`, so a separate OAuth trigger
isn't needed:

```sql
raw_nickname := coalesce(
  new.raw_user_meta_data->>'nickname',    -- email/password signup
  new.raw_user_meta_data->>'user_name',   -- Discord OAuth
  new.raw_user_meta_data->>'full_name',   -- future providers
  split_part(new.email, '@', 1)           -- last resort
);
clean_nickname := lower(left(regexp_replace(raw_nickname, '[^a-zA-Z0-9_.-]', '', 'g'), 32));
if length(clean_nickname) < 3 then
  clean_nickname := 'user_' || left(new.id::text, 8);
end if;
```

`coalesce` stops at the first non-null branch. For email/password signup,
`nickname` is always present (set via `options.data` in `use-register.ts`),
so the trigger only ever reads back what the user chose — the fallback
chain (`user_name` → `full_name` → email prefix → generated `user_<id>`)
only activates for OAuth accounts, which never had a nickname input to
begin with. The user-facing nickname is never overridden or regenerated
against their will on the email/password path.

**Accepted risk, applies to both paths:** a race window between the
uniqueness check and the actual insert (email/password), and no
pre-check at all for OAuth — the `unique` constraint on
`profiles.nickname` is the backstop in both cases, not the primary
mechanism. Acceptable at portfolio-project traffic, not a production-scale
guarantee.

## Alternatives Considered

**Auto-generate nickname from email prefix, dedupe via trigger loop**

- No extra form field, single round-trip signup
- Rejected: nickname the user never chose, no preview before account
  creation

**Catch uniqueness conflict from trigger failure, after `signUp()`**

- No separate pre-check query
- Rejected: `after insert` failure rolls back the whole transaction — user
  gets a generic Supabase error, not "nickname taken," and must retry
  `signUp()` with a different value

**Full transactional uniqueness check (advisory lock / serializable
transaction)**

- Eliminates the race condition entirely
- Rejected: complexity not justified at this scale; `unique` constraint
  backstop is sufficient — revisit only under real concurrent signup volume

**Force a "choose a nickname" step after Discord OAuth login**

- Would allow a pre-check for OAuth accounts too
- Rejected: extra UI surface not justified for a portfolio-scale project;
  SQL-level sanitization + accepted race risk is the simpler trade-off

## Consequences

- `registerSchema` requires `nickname` with the format constraints above;
  `register-form.tsx` has the corresponding field
- `use-register.ts` performs a `profiles` select before `signUp()`
- `handle_new_user()` needs `supabase db diff -f handle_new_user_trigger`
  (or a hand-written migration) committed — still only exists in local
  Supabase Studio, not on any deployed database
- OAuth-sourced nicknames have no uniqueness pre-check; a collision after
  sanitization fails the trigger insert with a generic error — accepted gap.
  If revisited: forced nickname-selection screen after first Discord login
  (rejected above as unnecessary UI overhead), tracked as optional in
  `docs/TODO.md` Slice 5 Polish
