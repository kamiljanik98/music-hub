# ADR-015: `useSearchSuggestions` — Debounce + Race Condition Guard

## Status: Accepted

## Date: 2026-07-23

## Context

The navbar search dropdown (ADR-014) fetches song title suggestions from
Supabase on every keystroke. Two problems come from that directly:

1. **Request volume** — firing a Supabase query on every keystroke sends
   far more requests than needed. Typing "reverb" naively fires 6
   requests instead of 1.
2. **Race condition** — even with debouncing, two requests can still be
   in flight close together (e.g. user pauses briefly mid-word). Network
   timing is not guaranteed to match request order: a later request
   (`"rockn"`) can resolve _before_ an earlier one (`"rock"`) if the
   earlier one is slower for any reason. Without protection, the earlier
   response arrives last and overwrites the dropdown with stale results
   that no longer match what the user has typed.

## Decision

`hooks/use-search-suggestions.ts` combines two mechanisms:

**1. Debounce (`hooks/use-debounce.ts`)**

Delays reacting to `query` until it stops changing for 300ms. Implemented
via `useEffect` + `setTimeout`, where the cleanup function clears the
pending timeout on every keystroke:

```ts
useEffect(() => {
  const timeout = setTimeout(() => setDebouncedValue(value), delay);
  return () => clearTimeout(timeout);
}, [value, delay]);
```

Only the last keystroke's timeout ever survives long enough to fire —
this cuts request volume but does not, by itself, prevent the race
condition above, since two debounced values can still trigger fetches
close enough together to resolve out of order.

**2. `cancelled` flag per effect run**

```ts
useEffect(() => {
  let cancelled = false;

  const fetchSuggestions = async () => {
    const { data } = await supabase.from("songs")...;
    if (!cancelled) setSuggestions(data ?? []);
  };

  fetchSuggestions();

  return () => {
    cancelled = true;
  };
}, [debouncedQuery]);
```

React runs an effect's cleanup function right before that effect re-runs
(triggered here by `debouncedQuery` changing). Each effect run closes
over its own `cancelled` variable. When `debouncedQuery` changes from
`"rock"` to `"rockn"`, React sets the _previous_ run's `cancelled` to
`true` before starting the new run. If the `"rock"` request resolves
after the `"rockn"` request, its own `if (!cancelled)` check is now
`false` — its result is discarded instead of overwriting the newer,
correct suggestions.

Net effect: only the response belonging to the most recent query is ever
allowed to update state, regardless of network timing.

## Alternatives Considered

**`AbortController`**

- Actually cancels the in-flight network request, not just its effect on
  state
- Rejected for now: `supabase-js`'s `.select()` chain doesn't expose a
  simple `signal` passthrough without extra wiring; the `cancelled` flag
  gives the same practical outcome (stale data never reaches the UI) with
  less code, at the cost of the stale request still completing
  server-side

**No guard, rely on debounce alone**

- Simplest, one less variable
- Rejected: debounce reduces request frequency but does not guarantee
  response order — the race condition is still possible, just less
  frequent

## Consequences

- Every future `useEffect`-based fetch-on-changing-input hook in this
  project should follow the same `cancelled`-flag pattern unless a
  stronger tool (`AbortController`) is introduced project-wide
- `useSearchSuggestions` never shows suggestions for a stale query, even
  under adverse network timing
- Trade-off accepted: the stale request still completes and consumes a
  Supabase call — this guards UI correctness, not network efficiency
