# ADR-006: Auth UI as Modal, Not Dedicated Pages

## Status: Accepted

## Date: 2026-06-17

## Context

Slice 1 of v0.2 Auth originally planned dedicated routed pages
(`app/(pages)/auth/register/page.tsx`, `login/page.tsx`, shared
`auth/layout.tsx`). Reconsidered against the SoundCloud-style public/private
UX already decided in ADR-004: sign in/register isn't a navigation event,
it's a modal opened from wherever the user is, closing it returns them to
the same context.

ADR-004 already established this for gated actions ("no route-based
redirect to `/auth/login`"), but assumed the modal would toggle visibility
for forms still living on dedicated pages. Building both — modal and pages
duplicating the same forms — means two parallel entry points to keep in
sync for no benefit at this scale. It also directly improves Event A (see
below): previously `router.push("/")` on successful register, discarding
whatever page the user was on; with a modal it's just `close()`.

## Decision

Auth UI (register, login) is a single modal, not routed pages. No
`/auth/register`, `/auth/login`, or `auth/layout.tsx` exist.

- `hooks/use-auth-modal.ts` — Zustand store (brought forward from v0.8 per
  ADR-004, extended beyond its original scope): `isOpen`,
  `view: "login" | "register"`, `open(view?)`, `close()`, `setView(view)`
- `components/auth/auth-modal.tsx` — single shadcn `Dialog`, switches
  `RegisterForm`/`LoginForm` by `view`, mounted once in root `layout.tsx`
- `components/auth/register-form.tsx` / `login-form.tsx` — pure form +
  hook call, no page-wrapper markup, render inside `DialogContent`
- Navbar gets Sign in / Register triggers calling
  `useAuthModal().open("login"|"register")`

**Toast Events — two distinct events, not to be conflated:**

- **Event A — register submit success.** `useRegister()` resolves without
  error → modal `close()` + toast "Check your inbox." Account is not
  confirmed yet, only the email was sent. Lives in `register-form.tsx`, not
  in the hook — `use-register.ts` stays routing/toast-agnostic, returns
  only `{ error }`.
- **Event B — confirmation link clicked.** Separate server-side flow, no
  toast, no modal auto-open — see ADR-005 for the redirect behavior. Since
  `auth/confirm` lands on a real page either way (`/auth/confirmed` or
  `/`), the modal's only entry points stay navbar + gated actions.

## Alternatives Considered

**Hybrid — pages as SEO/fallback surface, modal as primary entry**

- Answers direct links/bookmarks to `/auth/register`
- Rejected: builds a "page opens modal, redirects to `/`" mechanism for an
  edge case with no real traffic in a portfolio project

**Dedicated pages as originally planned, modal deferred to v0.8**

- No mid-milestone scope change
- Rejected: contradicts the SoundCloud UX already committed to in ADR-004;
  would require redoing Event A's `router.push` → `close()` change later
  anyway, plus a second migration once the modal is built

## Consequences

- `app/(pages)/auth/page.tsx`, `login/page.tsx`, `auth/layout.tsx` removed
  from v0.2 TODO entirely — not deferred, not kept as fallback
- `app/(pages)/auth/confirmed/page.tsx` remains the one real auth route —
  the email-link landing target, reached via `auth/confirm/route.ts`'s
  redirect, not app navigation
- `hooks/use-auth-modal.ts` moves up from v0.8 to v0.2 Slice 1, with an
  extended shape (`view`) beyond ADR-004's original spec
- No `/auth/login` or `/auth/register` URLs exist — direct links 404,
  accepted trade-off, no external inbound traffic to those paths
- Every future gated action (like, save, manage songs) opens the same
  modal via `useAuthModal().open()` — this ADR fully specifies what
  ADR-004 already pointed to, not a second mechanism
