# ADR-010: File Input — react-dropzone + Controller over Native ref

## Status: Accepted

## Date: 2026-06-25

## Context

`upload-form.tsx` used native `<input type="file">` with `ref` — `FileList`
doesn't fit `Controller`'s value contract, so file inputs were kept outside
RHF. This left them invisible to `fieldState` (no `invalid`, no `error`),
required manual `ref` management, and offered no drag-and-drop. Validation
lived entirely in the route handler with no client-side feedback.

## Decision

Replace native `ref` inputs with `react-dropzone` wrapped in `Controller`.
`FileList` was the mismatch, not `File` — `field.onChange` accepts a
`File` object directly.

`useDropzone` is called inside `Controller`'s `render` prop, not at
component top level. This is valid: `render` is a render function called
by React each render cycle, not a callback — Rules of Hooks aren't violated.

**`components/upload/form-input-file-audio.tsx`:**

- `field.onChange(acceptedFiles[0])` inside `Controller` render
- `AudioDropContent` subcomponent: file-selected / drag-active / empty states
- Dashed border via inline SVG `backgroundImage`, extracted to a
  `DASHED_BORDER` constant outside the component (stable reference)
- `role="button"` + `tabIndex={0}` — react-dropzone doesn't add these
  automatically when root props are spread
- Error display: `fileRejections[0]` (dropzone — size, type) takes
  priority over `fieldState.error` (RHF/Zod), single `<p>`

**`components/upload/form-input-file.types.ts`:**

`FormInputFileProps<T extends FieldValues>` — shared generic type across
file input components. Props: `name`, `control`, `label`, `onFileDrop?`,
`accept?`, `maxSize?`, `className?` — no `setValue` prop, eliminated by
`field.onChange`.

## Alternatives Considered

**Keep native `ref`, add client-side validation manually**

- Rejected: no `fieldState` integration, no drag-and-drop, manual ref
  management — more code for worse UX

**`Controller` with `setValue` as a prop** (allows `useDropzone` at top level)

- Rejected: `setValue` as a prop is a smell — `control` already gives
  form access; `field.onChange` inside `render` is the correct pattern

**Extract `useDropzone` to a wrapper component (`AudioDropzoneField`)**

- Rejected: adds a layer for a non-issue — `render` isn't a callback, so
  there's no Rules-of-Hooks ambiguity to avoid extracting for

## Consequences

- `upload-form.tsx` no longer uses native `ref` — replaced by
  `FormInputFileAudio`
- `FileList` no longer involved — `File` stored directly in RHF state,
  passed to `FormData` in `use-upload.ts`
- `form-input-file.types.ts` is the single type source for future file
  input components (cover input follows the same pattern)
- `react-dropzone` added as a dependency

## Update — 2026-07-24 (Stems: Dropzone Reverted to Plain `<input type="file">`)

`FormInputFileStem` simplified from `react-dropzone` back to a native
`<input type="file">`, wrapped in `Controller` (the `FileList`-vs-`File`
mismatch this ADR originally fixed still applies — `Controller` stays,
only `useDropzone` is removed). Judgment call: drag-and-drop UX for a
secondary, optional field (stems) wasn't worth the added complexity
`react-dropzone` brings for this one input — `FormInputFileAudio` (the
primary, required field) keeps the full dropzone pattern unchanged.

**Consequence:** client-side `maxSize` feedback (`fileRejections`) is
lost for stem files — oversized stem uploads now only surface as a
route handler error after submit, not before. Accepted trade-off at
this scale. This ADR's dropzone pattern is no longer a blanket rule for
every file input — `FormInputFileAudio`/`FormInputFileImage` (primary
fields) use dropzone, `FormInputFileStem` (secondary, per-row field in
a `useFieldArray`) does not. Future file inputs should default to
dropzone unless there's a similar "secondary/repeated field" reason not
to.
