# ADR-016: Social Schema — `follows`/`likes` RLS, Self-Follow Constraint, and Suggested Users

## Status: Accepted

## Date: 2026-07-29

## Context

v0.9 Social added two new tables, `follows` and `likes`, plus a "suggested users" feature on `/profile/[nickname]`. Three schema-level questions needed deciding before writing the server actions on top of them: how strictly to block self-follow, who can see who-follows-who, and how to pick which users to suggest. This ADR was planned back when the feature was first scoped but not written up until now — the schema below has been live and unchanged since.

## Decision

**1. Self-follow blocked at the DB level, not just app-layer.**

```sql
create table follows (
  follower_id uuid not null references auth.users(id) on delete cascade,
  following_id uuid not null references auth.users(id) on delete cascade,
  created_at timestamptz not null default now(),
  primary key (follower_id, following_id),
  check (follower_id != following_id)
);
```

Same reasoning as ADR-002's "RLS = DB layer, ownership check = app layer, both required": a `CHECK` constraint doesn't trust the UI or the server action to have prevented it correctly. `follow-user.ts` also blocks self-follow at the app layer (returns an error before attempting the insert), but the constraint is the real backstop.

**2. `follows` and `likes` are public-read.** Who-follows-who and who-liked-what are meant to be visible, the same way `songs` already is — this mirrors SoundCloud. Only `insert`/`delete` are restricted to the row's own owner:

```sql
alter table follows enable row level security;
create policy "public read" on follows for select using (true);
create policy "insert own" on follows for insert with check (auth.uid() = follower_id);
create policy "delete own" on follows for delete using (auth.uid() = follower_id);
```

`likes` (`user_id`, `song_id`, composite PK) follows the identical RLS shape — public read, insert/delete restricted to `auth.uid() = user_id`.

**3. Suggested users: random selection shuffled in application code, not SQL `ORDER BY random()`.** `getSuggestedUsers(excludeUserId)` fetches a bounded batch (3× the display limit) of candidate profiles — excluding the current user and anyone already followed — with a plain indexed query, then shuffles and slices to the final count (4) in JS. `ORDER BY random()` at the DB level forces a full-table sort on every request; at portfolio scale this doesn't matter yet, but the JS-shuffle approach was chosen because it's the same cost either way today and doesn't need revisiting if the user table grows.

## Alternatives Considered

**App-layer-only self-follow check, no DB constraint**

- Rejected: same reasoning as every other ownership check in this project (ADR-002) — the UI and the server action are not the last line of defense, the DB is.

**Private/friends-only follow visibility**

- Rejected: adds a permissions model with no product requirement behind it yet; public read matches the reference UX (SoundCloud) and is trivially reversible later (tighten the `select` policy) if privacy ever becomes a requirement.

**`ORDER BY random()` in SQL for suggested users**

- Rejected for now: simpler to write, but scans and sorts the whole `profiles` table on every request. The JS-shuffle-a-bounded-batch approach costs the same today and scales better without a rewrite later.

## Consequences

- Both tables initially hit `42501 permission denied` on insert after RLS was already correct — the missing piece was a **table-level `GRANT`**, a different failure mode than an RLS violation (which errors with "new row violates row-level security policy" instead). Fixed ad hoc for both tables; same root cause already tracked for `songs`/`stems`/`profiles`, all five now waiting on one bundled migration (see `docs/TODO.md`).
- The optimistic-UI pattern used by `use-follow.ts`/`use-like.ts` is documented once, in `docs/reference/CONVENTIONS.md`, not repeated per-table here — this ADR is schema/RLS/suggestion-algorithm scope only.
- Follower count and a "who follows me" list are not built — same public-read policy already supports it (query `follows` with `following_id = profileUserId` instead of `follower_id`), so adding it later needs no schema or policy change, just a new query.

## Update 2026-07-31 — `follows` FKs repointed at `public.profiles`; schema committed to a migration

The `create table follows` block above references `auth.users(id)`. That is what was live, and it silently broke `getFollowing()`.

**PostgREST resolves an embed only along a declared foreign key to the embedded table.** `get-following.ts` selects `profiles!following_id(id, nickname, avatar_url)`, but `follows.following_id` pointed at `auth.users`, and there is no FK from `follows` to `profiles` — so every call returned `PGRST200 — Could not find a relationship between 'follows' and 'profiles' using the hint 'following_id'`. Not a slow or partial failure: the action never returned data at all, while `docs/TODO.md` recorded it as done.

Both FKs now reference `public.profiles(id) on delete cascade`:

```sql
follower_id  uuid not null references public.profiles(id) on delete cascade,
following_id uuid not null references public.profiles(id) on delete cascade,
```

Cascade-on-user-delete is unchanged, just transitive — `profiles.id` itself references `auth.users(id) on delete cascade`. This also makes the not-yet-built `getFollowers` (Consequences, above) work by the same embed, and it is why `songs` embeds `profiles` correctly today: `songs.uploaded_by` already pointed at `public.profiles`.

`likes.user_id` was deliberately left pointing at `auth.users`. Nothing embeds a profile through `likes` — `get-liked-songs.ts` embeds `songs`, which reaches `profiles` via its own FK. If a "who liked this track" view is ever built, it needs the same repoint first.

**The grants tracked in Consequences are no longer ad hoc.** `supabase/migrations/20260731081353_social_schema.sql` now carries both tables, the enum, `profiles.bio`, the RLS policies and every grant. Two things that migration revealed:

- The `service_role` DML grants on `profiles`/`songs`/`stems` existed **only in the local database** — no migration ever created them. A deployment built from migrations alone would have given `service_role` no access to those tables and `npm run seed` would have failed on a fresh environment. `service_role` bypasses RLS but still needs table privileges. Granted for all five tables, so the seed script can also be extended to cover social data later.
- `follows`/`likes` never had `service_role` grants at all, which had not surfaced because the seed script doesn't touch them and `delete from profiles` cascades without needing them.

`supabase db diff` now reports no schema changes — the migrations directory is the schema of record again.
