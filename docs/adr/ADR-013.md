# ADR-013: Search — Server Action + SSR, Not Extending `useGetSongs`

## Status: Accepted

## Date: 2026-07-23

## Context

v0.6 Search needs to filter songs by `title`, `tags`, `genre`, `scale` and
render results at `/search?title=...`. `hooks/use-get-songs.ts` already
fetches the full song list client-side (Supabase directly, per
`docs/reference/CONVENTIONS.md` data fetching table) and feeds Discover/Feed cards plus
the player queue.

`docs/reference/CONVENTIONS.md`'s "jeden hook = jedno źródło prawdy" rule (extend a
shared hook instead of forking a duplicate query) suggested extending
`useGetSongs` with filter params instead of introducing a new server
action. That rule was written for same-shaped consumers (Discover cards,
Feed) sharing one client-side query — search is a different consumer
shape: a Server Component reading `searchParams`, not a client component
mounting a hook.

## Decision

`app/actions/get-songs.ts` — `getSongs(title?)` server action, called
directly from `app/(pages)/search/page.tsx` (Server Component). Not an
extension of `useGetSongs`.

Reasons:

- **SSR** — `/search` renders results in the initial HTML from
  `searchParams`, no client-side fetch waterfall after hydration. Matters
  for search specifically (perceived speed, no fetch flash); didn't
  matter for Feed/Discover, which are fine mounting client-side.
- **Query shape differs** — search needs `.or()` across `title`, `tags`,
  `genre`, `scale`; `useGetSongs` is a plain `select` for card display.
  Bolting conditional filter params onto `useGetSongs` would branch its
  one query into two different shapes depending on caller.
- **`searchParams` is a Server Component prop** — reading it server-side
  is direct; parsing it client-side to drive a hook would duplicate what
  Next.js already gives the page for free.

`useGetSongs` is unchanged, keeps serving Discover/Feed/cards exactly as
before — this isn't a second source of truth for the same query, it's a
different table access pattern for a different rendering strategy.

## Alternatives Considered

**Extend `useGetSongs` with optional filter params, call from
`SearchContent` (client component)**

- Matches `docs/reference/CONVENTIONS.md`'s existing hook-reuse rule literally
- Rejected: loses SSR on `/search` (results only after hydration), forces
  client-side `searchParams` parsing instead of the Server Component prop,
  and would make `useGetSongs` branch between two unrelated query shapes
  depending on whether filters are passed

**New client hook `useSearchSongs`, mirroring `useGetSongs`**

- Consistent hook-first pattern for search too
- Rejected: same SSR loss as above, plus a second hook duplicating
  `useGetSongs`'s Supabase-select boilerplate for no benefit

## Consequences

- `docs/reference/CONVENTIONS.md` data fetching table gets a new row: search results
  (SSR, filtered) → server action, not hook — distinct from the existing
  "Song list, metadata → Hook → Supabase directly" row, which still
  covers Discover/Feed
- `getSongs(title?)` lives in `app/actions/`, one file, per the existing
  "one file per server action" convention
- Any future SSR'd, filterable listing page follows this pattern (server
  action + Server Component), not a hook — `useGetSongs`-style hooks stay
  reserved for client-mounted, unfiltered, full-list consumers
