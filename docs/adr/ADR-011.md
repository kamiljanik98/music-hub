# ADR-011: `useCallback` dla handlera auto-advance w playerze

## Status: Accepted

## Data: 2026-07-06

## Kontekst

`components/player/controls.tsx` podpina `handleNext` pod `audio.onended`
do automatycznego przejścia na kolejny utwór. Bez memoizacji `handleNext`
powstaje na nowo przy każdym renderze, domykając ówczesne wartości
`ids`/`activeId`. Jeśli `onended` na `<audio>` nie zdąży się zaktualizować
zanim utwór się skończy, auto-advance działa na nieaktualnej kolejce —
przeskakuje na zły utwór albo w ogóle nie przechodzi dalej.

## Decyzja

`handleNext` i `handlePrev` owinięte w `useCallback` z
`[ids, activeId, setActiveId]` jako zależnościami — stabilna referencja
między renderami, dopóki kolejka lub aktywny utwór faktycznie się nie
zmienią, więc `audio.onended` zawsze wskazuje handler z aktualnym stanem.

```ts
const handleNext = useCallback(() => {
  if (!ids.length || !activeId) return;
  const currentIndex = ids.indexOf(activeId);
  const nextId = ids[currentIndex + 1] ?? ids[0];
  setActiveId(nextId);
}, [ids, activeId, setActiveId]);
```

## Rozważane alternatywy

**Brak memoizacji, `useEffect` odpalany przy każdym renderze**

- Odrzucone: restartowałoby `src`/`onended` na `<audio>` przy dowolnym
  renderze (np. zmiana głośności), psując płynność odtwarzania

**Ref z najświeższymi `ids`/`activeId` zamiast `useCallback`**

- Odrzucone: dodaje warstwę pośrednią (ref + efekt go aktualizujący) do
  problemu, który `useCallback` rozwiązuje wbudowaną memoizacją

## Konsekwencje

- Zależności `handleNext`/`handlePrev` muszą pozostać dokładne — pominięcie
  `ids` lub `activeId` przywróciłoby stale closure
- Przyszła zmiana sposobu przechowywania kolejki wymaga ponownej weryfikacji
  tej tablicy zależności
