# ADR-003: Testing Framework — Vitest over Jest

## Status: Accepted

## Date: 2026-06-05

## Context

v0.1 required a test suite covering env variables, Supabase connection and RLS (insert/select across `profiles`, `songs`, `stems`), server client initialization, and R2 connectivity via `HeadBucketCommand`. A testing framework had to be chosen before writing this suite.

Jest is the long-standing default for Next.js projects, but this project is ESM-first throughout (Next.js 16 with Turbopack, React 19, `@supabase/ssr`, AWS SDK v3) — Jest's CommonJS-oriented config needs extra transform setup (Babel or `ts-jest`) to handle ESM-only packages cleanly, and its cold start is noticeably slower.

## Decision

Use **Vitest** as the test runner for the entire project.

- Native ESM support — no extra transform config needed for ESM-only dependencies
- Built-in TypeScript support — no separate `ts-jest` or Babel step
- Significantly faster cold start and watch-mode re-runs than Jest, due to Vite's transform pipeline (esbuild vs Babel) and module-graph-aware re-runs in watch mode — exact multiplier depends on suite size and config, not independently benchmarked for this project
- API-compatible with Jest (`describe`, `it`, `expect`, mocking primitives) — existing Jest knowledge transfers directly, no new mental model
- Runs standalone — Vitest does **not** require the Vite bundler itself. `@vitejs/plugin-react` is only needed when a project is actually bundled by Vite; this project is bundled by Next.js/Turbopack, so the plugin is not installed

## Alternatives Considered

**Jest**

- Most mature ecosystem, most Next.js-specific documentation and examples
- Rejected: ESM interop requires extra configuration in an ESM-first project; slower cold start adds friction to the test-driven workflow used for v0.1 infrastructure verification

## Consequences

- Test files live in `__tests__/` at the project root — consistent with Next.js documentation examples
- No `jest.config.*` or Babel transform config needed; only a minimal `vitest.config.ts` if env loading (`.env.local`) is required for integration tests
- Integration tests require `supabase start` running locally; the R2 test requires network access to Cloudflare
- Future tests (v0.2 middleware onward) use the same Jest-compatible API — no framework decision needs revisiting per milestone
- Component tests (v0.2 onward — `RegisterForm`, `LoginForm`, `FormInput`) require `environment: "jsdom"` per-file plus `@testing-library/react`; this was not part of the original v0.1 scope but Vitest handles it without needing `@vitejs/plugin-react` (that plugin is for Vite-bundled projects, not for jsdom-based component testing) — see `docs/reference/CONVENTIONS.md` Testing section for the per-file setup
